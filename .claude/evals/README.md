# .claude/evals/ — проверка, что система работает (не «на ощущениях»)

Эвалы отвечают на вопрос: **стало ли реально лучше/хуже** после смены модели, правки `CLAUDE.md` или скила — или тебе только кажется?

## Зачем это нужно (реальный кейс)

Март–апрель 2026: Claude Code измеримо деградировал на шесть недель — не из-за модели, а из-за продуктовых изменений (reasoning, баг кэша, лимит длины). Команды без эвалов **чувствовали** «что-то не так», подкручивали промпты и адаптировались, но не знали причину до постмортема Anthropic. С эвалами ты ловишь это за час, а не за полтора месяца.

Тебе это особенно актуально: ты переключаешь модели (4.6→4.7→4.8), правишь универсальный `CLAUDE.md`, добавляешь хуки и субагентов. Каждое такое изменение может незаметно ухудшить поведение. Эвал — твой регрессионный детектор.

## Идея (без сложной инфры, для соло)

Это **не** промышленный eval-фреймворк с LLM-судьёй. Это набор «золотых задач» на твоём реальном коде + чёткие проверяемые критерии + способ прогнать их одинаково и сравнить. Логика как у тестов в коде:

- **baseline** — записал, как система отвечает сейчас (эталон).
- **regression** — после изменения прогнал снова, сравнил с эталоном.
- **outgrowth** — если задача проходит даже без твоего скила/правила, правило больше не нужно.

## Что считать «прошёл»

Каждый кейс имеет **объективный критерий**, проверяемый без вкусовщины: код компилируется, тест зелёный, нужный паттерн присутствует, файл создан/не создан, дизайн-токен использован вместо хардкода. Не «ответ хороший», а «выполнен ли критерий».

## Когда гонять

| Триггер | Что делать |
|---|---|
| Сменил модель (4.7→4.8) | Прогнать весь набор, сравнить с baseline |
| Поправил `CLAUDE.md` / playbook | Прогнать, убедиться, что не сломал поведение |
| Добавил/изменил субагента или хук | Прогнать релевантные кейсы |
| «Кажется, стало тупее» | Прогнать — подтвердить или опровергнуть фактами |
| Раз в месяц | Профилактика |

## Как устроено

```
.claude/evals/
├── README.md          ← этот файл
├── cases/             ← golden-задачи (по одной на .md)
│   ├── 01-surgical-edit.md
│   ├── 02-no-overengineering.md
│   ├── 03-checkpoint-protocol.md
│   └── 04-design-tokens.md
├── run_evals.py       ← раннер: гоняет кейсы через claude -p, проверяет критерии
└── baseline/          ← сюда пишутся эталонные результаты (--baseline)
```

## Как запускать

```bash
# Прогнать все кейсы, сравнить с baseline (если он есть)
python3 .claude/evals/run_evals.py

# Записать текущее состояние как эталон (после того как убедился, что всё ок)
python3 .claude/evals/run_evals.py --baseline

# Один кейс
python3 .claude/evals/run_evals.py --case 01-surgical-edit

# Без вызова модели — только проверить, что кейсы корректно описаны
python3 .claude/evals/run_evals.py --dry-run
```

Раннер использует `claude -p` (headless) — тот же механизм, что и рутины. Каждый кейс = полная сессия (учитывай лимиты).

## Важно про честность эвалов

- Кейсы должны быть **на твоём реальном коде/задачах**, а не абстрактные — иначе мерят не то.
- Начни с 4-6 кейсов, покрывающих то, что для тебя критично (хирургические правки, отказ от оверинжиниринга, протокол CHECKPOINT, дизайн-токены). Расширяй, когда ловишь реальный промах — добавляй его как новый кейс.
- Эвал проверяет **поведение твоей системы**, а не «умность модели вообще». Если кейс проходит без твоего правила — правило, возможно, лишнее (перерос).
