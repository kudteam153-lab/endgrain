# Пайплайн /design

Бриф: $ARGUMENTS

Выполни строго по фазам. НЕ пропускай фазы и НЕ объединяй их.

## Фаза 0 — Платформа и маршрут
Определи платформу по роутингу из `.claude/skills/design-tokens/SKILL.md`:
- **web** → генератор `design-generator-web`
- **mobile** → генератор `design-generator-mobile`
- **обе** (кросс-проект типа Detailbase, задача затрагивает и web и приложение) → ОДНА стратегия и ОДИН набор канон-токенов, затем оба генератора по очереди (web первым — на нём быстрее итерировать концепт, mobile вторым по утверждённым токенам).

Если в проекте есть brand-lock (проектные токены + пометка в CLAUDE.md) — фазы 1-2 пропускаются, концепт = существующая система, сразу Фаза 3.

## Фаза 0.5 — Ресёрч (только новые проекты/продукты)
Если проект новый (нет `design-output/research.md` и нет brand-lock) — запусти `design-researcher`. Выход: `design-output/research.md` (конкуренты, аудитория, конвенции ниши, зоны отстройки). Покажи пользователю «Открытые вопросы» из отчёта, если они есть. Для существующих проектов фаза пропускается.

## Фаза 0.7 — Структура
Запусти `design-architect`. Он изучает уже построенное (роутинг, навигация, лейауты), опрашивает по структуре и выдаёт `design-output/structure.md`: карта экранов, навигационная модель, приоритет контента по каждому экрану с обоснованием, потоки с точками решения, состояния.

Для лендинга фаза идёт в лёгком режиме — порядок секций и точки решения. Для правки в существующей структуре (`/design-quick`) пропускается. Стратег и критик дальше опираются на этот файл: первый строит концепты, зная устройство продукта, второй сверяет с ним иерархию.

## Фаза 1 — Стратегия
Запусти субагента `design-strategist` с брифом, платформой и `design-output/structure.md`. Стратег читает research.md (если есть) и базу ui-ux-pro-max (если установлена). Он вернёт анализ продукта + стилевую диагностику + 3 концепта с обоснованиями + рекомендацию. Концепты платформо-независимы (канон-токены), но стратег обязан учесть платформенные ограничения стиля (см. styles.md, сигнал №6).

## Фаза 2 — Выбор (СТОП-точка)
Покажи пользователю 3 концепта целиком (ASCII-наброски, обоснования цвета/шрифта, запрещённые стили). Дождись выбора. Можно смешивать или вернуть на доработку. БЕЗ выбора дальше не идти. Утверждённый концепт зафиксируй как канон-токены в `design-output/tokens.md`.

## Фаза 3 — Генерация
Запусти платформенный генератор (или оба по очереди — см. Фазу 0) с утверждённым концептом. Выход: код + скриншоты в `./design-output/screens/`.

## Фаза 4 — Критика (цикл)
Запусти `design-critic` со скриншотами и концептом. Критик сам читает вето-лог и режет кропы.
- REJECT / BLOCKER → правки генератору → новые скриншоты → снова критик.
- Если пользователь отклонил правку критика — она заносится в `## VETO` в `design-output/iterations.md`.
- Максимум 5 циклов; при «только MINOR» критик закрывает раньше.
Для кросс-задачи цикл проходится отдельно по каждой платформе, но изменения канон-токенов синхронизируются в обе.

## Фаза 5 — Сдача
Финальные скриншоты, путь к коду, 3-5 строк: какие решения приняты и почему, что критик заставил поменять.
