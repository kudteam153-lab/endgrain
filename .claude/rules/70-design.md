## 11. Дизайн-инвариант (если у проекта есть UI)

Правило подгружается при работе с UI-файлами, а не в каждой сессии: проекту без интерфейса оно не нужно. Механическая проверка от этого не зависит — хук `design-check.sh` работает всегда.

Дизайн-система — не «то, что надо помнить», а **проверяемый инвариант**:

- **Только токены.** Не хардкодить цвета (`#rrggbb`) и магические размеры — брать из дизайн-системы (`DESIGN_SYSTEM.md`, токены продублированы машинно в `.claude/design-tokens.json`).
- **Автопроверка.** После правки UI-файла хук `design-check.sh` сверяет токены и при отклонении возвращает замечание — Claude исправляет следующим шагом.
- **При работе над экраном** читать `playbook/screen-design.md`: обязательные состояния (empty / loading / error / …), 17-секционный шаблон, «что Claude НЕ делает в дизайне» (не выдумывать компоненты, endpoints, UX-текст).
- Файлы определения токенов (Theme.kt, tokens.css…) — единственное место, где хардкод цвета легитимен; они перечислены в `token_files` конфига.
