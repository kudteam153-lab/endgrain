## 4. Рабочий протокол

### 4.1. Перед задачей

Найти в `ROADMAP.md` → проверить Definition of Ready → проверить в `CHECKPOINT_CURRENT.md`, что зависимости закрыты. Что-то не так → сказать **до** старта.

### 4.2. Во время работы

- Не делать изменений вне scope. Баг в чужом модуле → отдельная задача, не «заодно».
- Conventional commits: `feat(M-XX): …`, `fix(M-XX): …`.
- Не пересматривать решения молча.

### 4.3. Пересмотр решения

Остановиться → сказать «требуется пересмотр #D-XX» → объяснить что и почему → после согласования новая запись `#D-YY` в `DECISIONS.md` со ссылкой на старую → старая получает статус `❌ отменено через #D-YY` → обновить затронутые файлы → проверить уже написанный код.

### 4.4. Завершение задачи

**Перед «готово» — само-pre-mortem (10 сек):** назови 2 конкретных способа, которыми изменение сломается (граничный вход, забытое состояние empty/loading/error, обратная совместимость, гонка, миграция данных) и проверь каждый. Не нашёл двух правдоподобных — изменение, вероятно, понято не полностью. Это самокритика *до* внешнего ревью, не вместо него. Это **микро**, код-уровень; стратегические риски проекта/фичи (монетизация, рынок, стек, регуляторка) — **макро**-скилл `pre-mortem` (Tiger / Paper Tiger / Elephant), запускается ДО стройки.

**На «готово» — отчёт «что НЕ проверено независимо» (анти-ложный-зелёный).** «Готово» не отдавать монолитом. Разделить явно: **(а) инструмент** — покрыто детерминированно (тесты / линт / типы / CVE), проверяемо без меня; **(б) только моё суждение** — код/логика, которую подтверждаю лишь я (тот же агент, что писал), независимый чек не касался; **(в) слепая зона Антона** — бэк/инфра/деньги, которые он не щупает сам. По (б)+(в) назвать конкретно, что осталось на доверии, и предложить дешёвый независимый чек (другая модель / враждебный прогон «сломай это» / поведенческий сценарий из UI). Доверие зелёному — информированное, не по умолчанию. См. LESSONS «Слепой принципал + агент сам себе проверяющий».

Code review **в свежем чате** (другой контекст = антипредвзятость) → approval Антона → merge → обновить `CHECKPOINT_CURRENT.md` (§1, §2.3, §3.3, §4 миграции, §8 следующая задача; можно командой `/checkpoint`) → если затронут API → §5; если было решение → §6 + `DECISIONS.md`.

**Закрытое не оставлять в рабочем файле:** исполненный или замещённый блок §8, записи §1/§2.3 прошлых сессий уезжают в архив тем же прогоном. Иначе чек-пойнт копит историю и через полгода перестаёт читаться за один вызов — это не гипотеза, так вышло в Detailbase (773 КБ, `Read` целиком уже не брал).

**Если чек-пойнт всё же разбух** — раскладка по жизненному циклу: `CHECKPOINT_CURRENT.md` (состояние + следующая задача) · `CHECKPOINT_DEBT.md` (открытый долг, пункты `[DBT-NNN]`) · `CHECKPOINT_API.md` (контракты, миграции) · `CHECKPOINT_ARCHIVE.md` (закрытое, append-only). Тогда адрес записи определяется типом факта, а не тем, какой файл открыт. Payload §4/§5/§7 уезжает, **заголовки §1–§10 остаются со строками-указателями и не перенумеровываются**: и SessionStart-хук, и `validate_checkpoint.py` читают раздел как «от `## N.` до `## N+1.`» и при пропаже заголовка молча отдают файл до конца. Инструмент — `.claude/scripts/rotate_checkpoint.py` (dry-run + два доказательства целостности; словари разметки настраиваются под проект).

### 4.5. Обновление документации

- Обновлять документы **целиком**, не патчами.
- Один факт — одно каноническое место. Повтор → cross-ref, не дублирование (дублирование = риск рассинхрона).

### 4.6. Контекст близок к лимиту

Автосжатие включено: при переполнении контекст суммируется сам, и работа продолжается — обрывать задачу заранее не нужно. `CLAUDE.md` в корне проекта переживает сжатие и перечитывается с диска; всё, что было сказано только в чате, — нет.

Что остаётся на исполнителе: не грузить целиком архивные чек-пойнты и большие реестры, читать файлы под задачу точечно. Правило «прочитал → использовал → выгрузил» описывало ручное управление, которого больше нет; смысл сохраняется как «не тащить в контекст то, что не нужно для текущего шага».

## 8. Антипаттерны (категорически избегать)

❌ Сразу писать код, не прочитав §1.

❌ Додумывать «вероятно, имелось в виду X» — остановиться и спросить (§2.1).

❌ Молча менять решения — только через `DECISIONS.md` (§4.3).

❌ «Заодно отрефакторить / удалить импорт / добавить поле на будущее» — §2.2–2.3.

❌ Длинное саммари «что я понял» — Антон знает контекст, кратко по §1.

❌ Применять принцип вне его контекста.

❌ Игнорировать `DECISIONS.md` при предложении решения — сперва проверить, нет ли уже.

❌ Угадывать API вместо проверки доки.
