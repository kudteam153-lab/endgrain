## 2. Принципы качества кода (Karpathy)

> Источник: наблюдения Карпаты о типовых провалах LLM в коде. Принципы смещают баланс к **осторожности**, а не скорости. Для тривиального (опечатка, очевидный one-liner) — здравый смысл, полная строгость не нужна.

### 2.1. Думай перед кодом

- Озвучивай допущения явно. Не уверен — спрашивай, не угадывай.
- Несколько интерпретаций — показывай все, не выбирай молча.
- Есть путь проще — скажи. Возражай, когда оправданно.
- Что-то неясно — остановись, назови что именно, задай вопрос.

### 2.2. Простота прежде всего

- Никаких фич сверх запрошенного.
- Прежде чем писать своё, ищи готовое — по порядку: уже есть в кодбазе → stdlib → нативная фича платформы → установленная зависимость → только потом свой код.
- Никаких абстракций для одноразового кода.
- Никакой «гибкости/конфигурируемости», которую не просили.
- Никакой обработки невозможных ошибок.
- Написал 200 строк, а можно 50 — перепиши.

### 2.3. Хирургические правки

- Не «улучшай» соседний код, комментарии, форматирование.
- Не рефактори то, что не сломано. Соблюдай существующий стиль.
- Заметил несвязанный мёртвый код — упомяни, не удаляй.
- Удаляй только тех «сирот», которых создали твои же изменения.
- **Тест:** каждая изменённая строка вытекает напрямую из запроса.

### 2.4. Цели вместо команд

Превращай задачу в верифицируемую цель:

| Вместо             | Используй                                                |
| ------------------ | -------------------------------------------------------- |
| «Добавь валидацию» | «Тесты на невалидные входы → потом сделай, чтобы прошли» |
| «Исправь баг»      | «Тест, воспроизводящий баг → потом исправь»              |
| «Отрефактори X»    | «Тесты зелёные до и после»                               |

Сильные критерии успеха = работа в цикле без постоянных уточнений.

**Словарь теста.** Три понятия, без которых «покрыто тестами» ничего не значит:

- **Шов** — публичная граница, на которой наблюдают поведение, не залезая внутрь. Тест ставится только на согласованном шве: **до написания теста назови шов и подтверди его у Антона.** Тест, прибитый к внутренностям, ломается при рефакторинге, хотя поведение не менялось.
- **Тавтологический тест** — утверждение пересчитывает ожидаемое так же, как это делает код. Проходит по построению и не способен разойтись с кодом. Ожидаемое значение берётся из независимого источника: ручной расчёт, зафиксированный образец, спека.
- **Горизонтальная нарезка** — написать все тесты вперёд, до реализации. Они проверяют воображаемое поведение. Вместо неё вертикальные срезы: один шов → один тест → минимальная реализация → следующий. Каждый тест — трассирующая пуля, а не часть заранее уложенного слоя.

Рефакторинг живёт в ревью, а не в цикле «красный → зелёный».

**Маркеры, что принципы работают:** меньше лишнего в diff; меньше переписываний из-за переусложнения; уточняющие вопросы — до реализации, а не после ошибок; чистые минимальные PR.

## 7. Шаблон критериев успеха (применение §2.4)

Любую нетривиальную задачу формулировать как верифицируемую цель: **артефакт + что покрыто + чем проверяется + как выглядит «зелёным»**.

Пример (обобщённо):

> «<Компонент / endpoint / миграция> делает X. Покрыто: <валидные / невалидные / граничные входы>. Проверка: <тесты / команда / критерий>. Состояния (если UI): empty / loading / error. Затронутую доку обновить целиком (§4.5).»

Проектные шаблоны (backend, миграция, UI-компонент, экран) — в профильных файлах пакета, не здесь.
