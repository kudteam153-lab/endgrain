# GOAL_GUIDE — как завести цель-якорь на любой проект

> Переносимый шаблон. Кладётся в ядро (рядом с `CLAUDE.md` или в `playbook/`). Объясняет, как создать `GOAL.md` + `goal.json` для нового проекта. Эталонный пример — `GOAL.md` проекта ai-harness.

---

## Когда заводить

В начале проекта (фаза Seed или сразу после закрытия ТЗ). До первой строки кода — чтобы было с чем сверять дрейф.

## Что это и чем отличается от соседей

| Файл | Отвечает на вопрос |
|---|---|
| **GOAL.md** | Зачем всё это и как поймём, что готово |
| CORE_PRINCIPLES.md | По каким принципам работаем / что НЕ делаем |
| ROADMAP.md | В каком порядке делаем |
| CHECKPOINT §8 | Что делаем прямо сейчас (задачная цель) |

GOAL — самый верхний и самый стабильный слой. Один на проект.

## Структура (три части, ничего лишнего)

1. **Цель** — 1 абзац. Для кого, какую боль закрывает, как выглядит «достигнуто».
2. **Acceptance** — 3–7 **проверяемых** критериев. Каждый — наблюдаемое да/нет, тест или артефакт. Не «улучшить X», а «X делает Y, проверяется Z».
3. **Anti-scope** — явный список «что НЕ входит». Это главное оружие против scope-creep и «агент добавил от себя». Пиши сюда всё, что соблазнительно сделать, но не нужно для цели.

## Правила

- **Immutable.** После принятия не правится по ходу. Изменение цели — только через `DECISIONS.md`: новая запись, старый GOAL помечается отменённым (`supersedes`). Это и защищает от тихого дрейфа.
- **Две копии синхронно.** `GOAL.md` (читаемо для человека) + `goal.json` (машинно для хука `gate-goal`). Как `DESIGN_SYSTEM.md` ↔ `design-tokens.json`. Поменял одно — поменяй второе.
- **Перечитывать.** На каждой существенной точке решения сверяйся с acceptance и anti-scope. `gate-goal` напоминает об этом на завершении крупного хода.
- **Не дублировать план.** Этапы и текущая задача — в ROADMAP / CHECKPOINT §8, не здесь. GOAL фиксирует рамку, не маршрут.

## Как формулировать acceptance (проверяемо)

| Плохо (непроверяемо) | Хорошо (проверяемо) |
|---|---|
| «Сделать удобную память» | «Агент на старте получает состояние всех проектов из ai-memory без ручного ввода» |
| «Контролировать решения» | «High-risk действия эскалируются человеку; решения append-only в DECISIONS» |
| «Сделать быстро» | «6 acceptance закрыты, gate-goal зелёный, существующее не сломано» |

### Для продуктовых проектов — PMF в acceptance

Когда цель — продукт для реальных юзеров, часть acceptance можно сформулировать как проверяемый product-market fit (детали и litmus — `playbook/phases.md §Гейт PMF`):

| Непроверяемо | Проверяемо (PMF-litmus) |
|---|---|
| «Продукт зашёл» | «>40% активных в тесте Sean Ellis отвечают „очень расстроюсь“ без продукта» |
| «Есть retention» | «Day-30 retention ≥ X% держится 3 итерации подряд, не разовый всплеск» |
| «Юзеры довольны» | «Продукт удерживает без ручного аутрича основателя — effort-тест пройден» |

Anti-scope здесь же фиксирует ложные позитивы, которые НЕ считаем успехом: signups без активации, revenue без retention.

## Минимальный шаблон goal.json

```json
{
  "id": "GOAL-<project>",
  "project": "<project>",
  "immutable": true,
  "supersedes": null,
  "status": "active",
  "updated": "YYYY-MM-DD",
  "goal": "<1 абзац>",
  "acceptance": [
    { "id": "A1", "text": "<критерий>", "verify": "<чем проверяется>" }
  ],
  "anti_scope": [ "<что НЕ входит>" ]
}
```
