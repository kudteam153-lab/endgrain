# PROJECT METHODOLOGY PLAYBOOK
## Универсальная методология работы с Claude над проектами — ядро

> **Назначение.** Переносимая методология запуска и ведения проекта с Claude как техническим соавтором. Извлечена из практики Detailbase (B2B SaaS CRM, ~9 мес., ~2000 строк ТЗ, ~13 экранов, ~230 решений).
>
> **Это ядро.** Здесь — суть, философия и **маршрутизатор**: какой reference-файл читать под какую задачу. Тяжёлые детали (фазы, шаблоны пакета, формат решений, 17-секционный экран, чек-листы) вынесены в `playbook/` и грузятся только по необходимости — это экономит контекст. **Не читай reference-файлы целиком наперёд; иди по §«Маршрутизатор».**
>
> **Поведение Claude в сессии** — `CLAUDE.md`. **Старт чата** — `CHAT_HANDOFF.md`.

## 0. TL;DR — суть в 10 строк

1. **Один источник истины** — пакет md-файлов в Project Files, не разрозненные заметки.
2. **Точка входа** — `NAVIGATION.md` + `CORE_PRINCIPLES.md` + `CHECKPOINT_CURRENT.md` читаются в начале каждого чата.
3. **Append-only журнал решений** — `DECISIONS.md`, всё с альтернативами и причиной.
4. **Краткий саммари** — «Контекст восстановлен. Сейчас: … Следующая задача: …» и ждать.
5. **Принципы НЕ нарушаются молча** — нарушение = остановка + обсуждение + запись в DECISIONS.
6. **Cross-refs по единому стандарту** — `FILE.md §X.Y`, `FILE.md #Entity`, `#D-XX`, `#US-XXX`.
7. **Микро-задача в фокусе** — `CHECKPOINT_CURRENT.md §8` всегда содержит ультра-конкретное «дальше».
8. **DoR / DoD** на каждой задаче и итерации.
9. **Шорткаты** — «Подтверждаю», «Стоп», «Запиши решение», «Чек-пойнт» (полный список — `CLAUDE.md §6`).
10. **Не додумывать** — при сомнении остановка и вопрос.

## 1. Философия

### 1.1. Базовый закон

> **Чат — рабочее место. Файлы — память. Антон — арбитр.**

Claude в каждом чате стартует с нуля, поэтому вся память проекта живёт в файлах. Чат — партия по уже расставленной доске; расстановку (файлы) поддерживают Антон и Claude в конце каждой значимой задачи.

### 1.2. Почему обычная работа ломается на больших проектах

| Симптом | Причина | Решение |
|---|---|---|
| Claude забывает контекст через 30 сообщений | Окно контекста конечно | Состояние в файлах, не в чате |
| Переспрашивает утверждённое | Нет канона | `CORE_PRINCIPLES` + `DECISIONS` как правда |
| В новом чате противоречит старому | Каждый чат изолирован | `CHECKPOINT_CURRENT` сшивает чаты |
| Решения «расплываются» | Нигде не записаны | Append-only `DECISIONS` |
| Cross-refs не работают | Имена расходятся | Единый стандарт якорей |
| Файлы дублируют друг друга | Нет карты | `NAVIGATION` фиксирует «где что» |
| Большой документ не читается за чат | Контекст лопается | Один файл → 12–15 профильных + раскрытие |

### 1.3. Эволюционный закон пакета

Три стадии: **Seed** (1 файл `PROJECT_MASTER.md`, до ~500 строк) → **Split** (12–15 файлов, при >1500 строк или когда чат не читает целиком) → **Surface** (+ файлы по поверхностям UI).

Сигнал к разбиению: файл > 1000 строк, либо один факт в 3+ файлах.

## 2. Правило «3 файла + N по задаче»

В любом чате Claude обязательно читает: `NAVIGATION.md` → `CORE_PRINCIPLES.md` → `CHECKPOINT_CURRENT.md`. Дальше — только нужное под задачу по таблице маршрутизации из `NAVIGATION.md`.

**Антипаттерн.** Не грузить всё. Бюджет контекста тратится на работу, а не на справку. То же касается этого playbook: грузи reference-куски точечно (см. ниже).

## 3. Маршрутизатор playbook — что читать под задачу

## 4. Метрики качества пакета (быстрый ориентир)

| Метрика | Цель | Тревога |
|---|---|---|
| Один файл | < 1000 строк | > 1500 → дробить |
| Дублирование факта | 1 canonical-место | 3+ → выбрать canonical, остальное cross-ref |
| Cross-refs | Работают через `#anchor` | Битая ссылка → fail health-чека |
| Time-to-context новый чат | < 30 сек после 3 файлов | > 2 мин → проблема в `CHECKPOINT_CURRENT` |
| Покрытие решений | Каждый спор задокументирован | Тихие изменения = плохо |

Подробные шаблоны и группы файлов — `playbook/package-templates.md`.
