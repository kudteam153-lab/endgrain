## Seed-шаблон (одиночный файл, ранняя фаза) {#seed}

```markdown
# PROJECT MASTER — <Название>

## 0. Мета
- Название, этап, язык работы, разработчики, география.

## 1. Что уже утверждено
### 1.1. Рыночная гипотеза
### 1.2. Архитектурные принципы №1 (что мы НЕ делаем)
### 1.3. Технологический стек
### 1.4. Бизнес-модель (тарифы / другая монетизация)
### 1.5. Фазы запуска (1–4)
### 1.6. Полный реестр фич (пронумерован)
### 1.7. UX-принципы
### 1.8. Критерии успеха и red flags

## 2. Связанные артефакты (research, бренд, репозитории)
## 3. Открытые вопросы (с deadlines)
## 4. Правила работы Claude (краткие)
## 5. Changelog
```

## Зрелый пакет — 12–15 файлов

### Группа A. Стратегические (3 файла, всегда читать)

| Файл | Содержимое | Объём |
|---|---|---|
| `NAVIGATION.md` | Карта файлов + маршрутизация «задача → файлы» + стандарт cross-refs | ~250 |
| `CORE_PRINCIPLES.md` | Видение, 10 принципов, UX-принципы, архитектура ядра, фазы, открытые вопросы | ~250 |
| `CHECKPOINT_CURRENT.md` | Снимок состояния. §8 «следующая микро-задача» — критичен | ~200 |
| `CHECKPOINT_DEBT.md` · `CHECKPOINT_API.md` · `CHECKPOINT_ARCHIVE.md` | Появляются, когда чек-пойнт перерос бюджет старта: долг · контракты и миграции · закрытое. Читаются точечно, не при каждом старте | без лимита |

### Группа B. Контентные (8–10 файлов, читать по задаче)

| Файл | Содержимое |
|---|---|
| `ROLES_PERSONAS.md` | Роли (внутр. + внешн.) + персоны + матрица прав |
| `DOMAIN_MODEL.md` | Сущности с якорями, FSM, инварианты, индексы, ER-связи |
| `USER_STORIES.md` | US с приоритетами + E2E-сценарии + INDEX |
| `MODULES.md` | Модули с зависимостями, волнами, ключевыми решениями |
| `INTEGRATIONS.md` | Внешние API с `#I-XX`, статусом, причиной |
| `NFR.md` | 12 категорий: SLA, безопасность, ФЗ/GDPR, a11y, производительность |
| `ANALYTICS.md` | NSM, бизнес-метрики, события, retention, opt-out |
| `<DOMAIN>_BUSINESS.md` | Тарифы / unit-экономика / комиссионная модель |
| `<SPECIAL>.md` | Спецразделы (ЗП-конструктор, AI-логика) |
| `ROADMAP.md` | Итерации, вехи, DoR/DoD, риски |

### Группа C. Журналы и состояние (3 файла, непрерывно)

| Файл | Содержимое | Кто обновляет |
|---|---|---|
| `DECISIONS.md` | Append-only журнал `#D-XX` | Claude после каждого решения |
| `FACTS.md` | Память фактов `#F-XX`: выжимка + источник + срок годности | Claude, когда факт добыт или протух |
| `SCHEMA.md` | Текущее состояние БД (автогенерация) | Автоматически после миграций |
| `CHAT_HANDOFF.md` | Как стартовать чат | Антон, редко |

### Группа D. Поверхностные (при переходе к UI)

| Файл | Содержимое |
|---|---|
| `DESIGN_SYSTEM.md` | Токены, типографика, компоненты, motion, tone of voice |
| `SCREENS_CHECKPOINT.md` | Протокол экранов + 17-секционный шаблон |
| `SCREENS_WEB.md` / `_FLUTTER.md` / `_PWA.md` | Реестры экранов по поверхностям |

### Группа E. Архив

| Файл | Содержимое |
|---|---|
| `PROJECT_MASTER.md` | Изначальный Seed — read-only как историческая ссылка |
| `CHECKPOINT_ITERATION_N.md` | Снимки прошлых итераций |
| `Research_Report.md` | Customer Development и анализ рынка |

## Change-юнит — единица изменения между итерацией и микро-задачей {#change-unit}

Между **итерацией** (ROADMAP, ~2 недели, модуль) и **микро-задачей** (`CHECKPOINT §8`, один шаг) нет первоклассного объекта на «одну связную фичу». Из-за этого рассуждение о фиче размазано: зачем — в `DECISIONS`, когда — в `ROADMAP`, сейчас — в `CHECKPOINT`, что — в каноне. Нельзя указать на «изменение X» и отревьюить/откатить его как целое.

Change-юнит — папка, которая это собирает. Заводится и закрывается вручную (команды `/propose`/`/apply` удалены 2026-07-26 — не вызывались ни разу).

```
changes/<name>/
  proposal.md   зачем + scope + anti-scope изменения + «затрагивает канон» (ссылка на GOAL #A)
  tasks.md      шаги — единственный трекер, пока change активен (CHECKPOINT §8 ссылается, не дублирует)
changes/archive/<name>/   закрытые
```

**Что даёт на уровне системы.** Из трёх стабильных слоёв два защищены от тихого дрейфа (`GOAL` immutable, `DECISIONS` append-only), а **канон/`wiki` правится молча по ходу** — единственная щель. Закрытие change делает обновление канона одним гейтированным переходом: правка канона трассируется к `#D-XX` и закрытому change. Плюс достраивает поток знаний — `raw → change (in-flight) → wiki`: «оформлено, но ещё не канон» получает дом.

**Границы (не плодить третий трекер).**
- Пока change активен — шаги живут только в его `tasks.md`; `CHECKPOINT §8` на него **ссылается**, шаги не перечисляет.
- `ROADMAP` остаётся уровнем итерации/модуля; change — уровень фичи под ним.
- Change без архитектурного решения (чистая реализация без альтернатив) при закрытии **не** заводит запись в `DECISIONS` — только обновляет канон, если тронул.
- Мелкому проекту без частых фич change-юнит необязателен — это инструмент, когда фич-поток есть.

## Поток знаний: raw → wiki (двухслойная база) {#raw-wiki}

Для доков-репо (особенно Obsidian-vault) — **двухслойный поток**: отделяет «сырое» от «утверждённого», чтобы пакет оставался каноном, а мысли и отказы не терялись.

| Слой | Что лежит | Дисциплина |
|---|---|---|
| `wiki/` | **Утверждённое** — весь пакет (группы A–E выше). Источник истины. | Только после явного «ок». Один факт — одно место. |
| `raw/` | **Поток** — append-only: незрелые идеи, обратная связь, конкурентный анализ, **отброшенные альтернативы с причиной отказа**, открытые вопросы. | Заметки **не редактируем и не удаляем** — добавляем новые с датой. |
| `inbox/` | Быстрые неразобранные заметки (разобрать → `raw/` или `wiki/`). | — |
| `chats/` | Экспорты значимых сессий (хэндофы между чатами). | — |

**Правила потока:**
- В `wiki/` запись попадает, когда из 3–5 `raw/`-заметок **кристаллизовался устойчивый ответ** (утверждает арбитр).
- Миграция `raw → wiki`: raw **не удаляем**; в wiki-записи ставим обратную ссылку `Источник: raw/<...>` — сохраняет «почему».
- **Перед правкой канон-дока** — `grep` по `raw/` на связанные заметки; **не возвращаемся к отброшенному варианту без обсуждения** (его причина отказа лежит в `raw/`).
- Naming: `raw/` и `chats/` — `YYYY-MM-DD-topic-kebab.md` (дата в начале); `wiki/` — `UPPER_SNAKE.md`.

> **Зачем.** «Утверждённое» не мешается с «черновым»; отказы не теряют причину (через год не переоткроют закрытый спор); пакет читается как чистый канон. Для flat-проекта без vault слой `raw/` всё равно полезен — фиксировать мысли, не засоряя канон. Захват в `raw/` удобно автоматизировать project-скилом (как `*-raw-capture` в Detailbase).

## Раскладка `wiki/` по подпапкам (рекомендация) {#wiki-layout}

Когда пакет растёт, `wiki/` удобно делить на **нумерованные подпапки по концерну** (номер = примерный порядок чтения). Группы A–E ложатся так:

```
<repo>/
├── CLAUDE.md  NAVIGATION.md  CHECKPOINT_CURRENT.md  CHAT_HANDOFF.md   ← в корне (читаются первыми)
├── wiki/
│   ├── 00-core/      CORE_PRINCIPLES · DOMAIN_MODEL · MODULES · NFR · DECISIONS · DESIGN_SYSTEM · SCHEMA   (A-ядро, B, C, D-дизайн)
│   ├── 01-screens/   SCREENS_<surface> + по экрану SCR-…              (D)
│   ├── 02-business/  ROADMAP · USER_STORIES · ROLES_PERSONAS · <DOMAIN>_BUSINESS   (B бизнес)
│   ├── 03-research/  Research_Report · custdev · среда                (вход/архив)
│   └── 04-handoff/   DEV_HANDOFF (мост спека→код) + role-handoff'ы
├── raw/  inbox/  chats/   ← поток знаний (§raw-wiki)
└── .claude/  playbook/
```

- **В корне** — только то, что читается в начале **каждого** чата: `NAVIGATION` + `CHECKPOINT_CURRENT` (+ `CLAUDE.md`/`CHAT_HANDOFF.md`). `CORE_PRINCIPLES` — в корне или `00-core/` (тогда обязательный минимум ссылается туда).
- **Автоматика видит доки по путям:** если они в подпапках, пути в командах/агентах/хуках это учитывают (напр. `wiki/00-core/DECISIONS.md`, `/debt` → `wiki/02-business/ROADMAP.md`). При раскладке плоско — голые имена.
- Раскладка **опциональна:** мелкому проекту хватит плоского `wiki/` или корня. Номера дают порядок и навигацию, когда файлов много (10+).

## Метрики качества пакета (полная версия)

| Метрика | Цель | Тревога |
|---|---|---|
| Один файл | < 1000 строк | > 1500 → дробить |
| Дублирование факта | 1 canonical | 3+ → canonical + cross-ref |
| Cross-refs | Работают через `#anchor` | Битая ссылка → fail health-чека |
| Time-to-context | < 30 сек после 3 файлов | > 2 мин → проблема в `CHECKPOINT_CURRENT` |
| Покрытие решений | Каждый спор задокументирован | Тихие изменения = плохо |

> Для очень крупных файлов группы B (DOMAIN_MODEL, USER_STORIES) применяй внутреннее раскрытие: ядро = список + связи, детали по сущности/US — отдельными кусками, тянутся по якорю.
